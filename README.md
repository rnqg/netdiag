# netdiag

Консольная диагностика сети для российских пользователей и технической поддержки. Утилита проверяет доступность сервисов, измеряет качество подключения, испытывает варианты решения и сохраняет доказательства в отчёте.

Текущая версия — `0.1.3`. Есть клиент для Windows, macOS и Linux и необязательный измерительный узел. Для обычной диагностики сервер и учётная запись не нужны.

## Запуск

```sh
netdiag
netdiag check --mode direct --output direct.json
netdiag check --mode vpn --target example.org --verbose
netdiag check --mode direct --full --trace --node https://node.example.org:8443 --output full.json
netdiag check --mode direct --only-target --target example.org --profile quick
netdiag compare --baseline direct.json --mode vpn --output comparison.json
netdiag quality --mode direct --duration 60s
netdiag report --input direct.json --verbose
```

Без аргументов предлагается подтвердить режим подключения. Признаки VPN определяются по интерфейсам; это подсказка, а не доказательство маршрутизации. В автоматическом запуске режим задаётся явно.

`direct` выбирает Яндекс, Mail, VK, Ozon, Госуслуги и Rutube. `vpn` выбирает YouTube, Telegram Web, Discord, WhatsApp Web, GitHub и Wikipedia. Каталог не гарантирует доступность площадок. Проверка сайта не проверяет звонки, воспроизведение видео и авторизацию в приложении.

С флагом `check --full` в один отчёт попадают доступность, RTT и джиттер, размеры UDP-пакетов, скорость и задержка под нагрузкой. Нужен свой `--node`. Этапы идут последовательно. Длительность исходного замера качества задаёт `--duration`, а `--max-mib` делится между замерами качества и нагрузки. Если не получены все три замера задержки под нагрузкой, полный отчёт помечается частичным. `--trace` добавляет трассировку. `compare` по полному отчёту повторяет проверки доступности.

По умолчанию используется профиль `deep` с общим сроком до 180 секунд. `quick` ограничен 60 секундами. Проверки отдельных этапов имеют меньшие сроки ожидания. Для отдельного замера скорости и задержки под нагрузкой используйте `speed`. Профиль `deep` задаёт глубину проверки доступности и протоколов. Для проверки буферблоата нужен свой измерительный узел; M-Lab измеряет только скорость. Сравнение повторяет цели и профиль исходного отчёта, а не подменяет их каталогом другого режима.

Цель — HTTP(S) origin. Путь, пароль, параметры и фрагмент введённого URL отбрасываются. Не передавайте ссылки подписок и другие секреты вместо домена. До 16 целей, повторяющийся `--target` добавляет их к каталогу. `--only-target` отключает каталог.

## Что измеряется

| Область | Проверки |
| --- | --- |
| Подключение | Интерфейсы, MTU интерфейса, маршрут, шлюз, признаки VPN и прокси, изменение сети |
| Wi-Fi | Доступные радио-параметры через средства ОС; отсутствие разрешения отмечается явно |
| DNS | Разрешение имён утилитой, A/AAAA, время ответа; матрица UDP/TCP/DoH/DoT для первой цели, два запроса A и отрицательный контроль; IPv6-адреса резолверов при наличии IPv6-адреса, отличного от link-local |
| Соединение | TCP-подключение, отдельные попытки подключения, IPv4/IPv6, статистика TCP из API ОС при открытии и при чтении первых 64 КиБ ответа |
| TLS | Проверка цепочки и имени, сроки сертификата, TLS 1.2/1.3, согласованный протокол |
| HTTP | HTTP/1.1 и HTTP/2; HTTP/3 по поддерживаемому объявлению Alt-Svc; ответы, ограничения и перенаправления внутри origin |
| Качество | ICMP RTT; с узлом — UDP RTT, потери ответов, серии потерь, дубликаты, перестановка и вариация RTT |
| Размеры пакетов | UDP-пробы с запретом фрагментации, если его поддерживает ОС; подтверждённый проходящий размер, а не выдуманный точный PMTU |
| Скорость | M-Lab NDT7 либо свой узел; с узлом — один и несколько отдельных TCP-соединений, загрузка, отдача и двусторонняя нагрузка |
| Задержка под нагрузкой | Один и тот же UDP-узел до нагрузки, во время неё и после; проверка варианта с ограничением создаваемой нагрузки |

Запросы идут напрямую по маршрутам ОС. Системный HTTP-прокси, PAC, переменные proxy и браузерные расширения не воспроизводятся как путь пользовательского приложения. При признаках прокси это отражается в заключении. Системный туннель VPN применяется маршрутизацией ОС; утилита не подключает и не переключает VPN.

ICMP IPv4 использует непривилегированные сокеты на macOS/Linux и штатный API на Windows. На Linux это зависит от `ping_group_range`. При отсутствии доступа утилита не требует запуска всей диагностики от администратора и не подменяет RTT временем HTTP-ответа.

## Методика

RTT ICMP, RTT UDP, оценка RTT ядром TCP, время TCP-подключения и время первого байта — разные показатели.

Перцентили вычисляются методом nearest-rank. p99 появляется при 100 успешных пробах. Джиттер RTT — среднее `abs(RTT[i] - RTT[i-1])` для соседних успешных последовательных проб, без соединения значений через пропущенный пакет. Это не оценка односторонней вариации задержки и не RTP jitter.

Локальная ошибка отправки учитывается отдельно от потерь: `attempts` — все попытки, `sent` — успешно отправленные пробы, `local_send_errors` — ошибки отправки. Поздние UDP-ответы отмечаются в `late_replies`, но не становятся успешными RTT-пробами. Пропущенный ответ учитывается после срока ожидания. Для UDP это 750 мс, интервал отправки 100 мс. Для ICMP — 900 мс и 1 секунда соответственно. «Потеря пробы» не означает установленную потерю такого же процента всех пакетов сети.

Для задержки под нагрузкой используется разница p95 UDP RTT до того же узла. Первые пять секунд исходного и нагрузочного интервала исключаются из этого расчёта. Нужны как минимум 50 успешных проб в каждом используемом интервале, продолжающаяся передача данных во всех потоках и завершённый нагрузочный интервал. После каждого этапа проверяется восстановление; сохраняющийся рост задержки отмечается неоднозначным. Насыщение линии не объявляется доказанным: отсутствие роста задержки не доказывает отсутствие буферблоата при другой нагрузке.

При росте p95 от 20 мс и восстановлении задержки после нагрузки испытывается ограничение до 70% наблюдаемой суммарной скорости. После основных замеров выполняется серия A–B–A: обычная нагрузка, ограниченная, снова обычная. Все интервалы по 10 секунд, первые три секунды исключаются. Нужны минимум 50 успешных проб в каждом интервале, завершённая передача по всем потокам, снижение p95 минимум на 20% относительно обеих контрольных нагрузок без роста потерь и восстановление после каждого этапа. Системные настройки не меняются.

Рост задержки может включать локальное планирование процессов и обработку на узле. Узел тоже может ограничивать скорость. Измерения нельзя автоматически приписывать провайдеру или роутеру.

## Проверка решений

При сбое веб-цели испытываются альтернативные DNS. Автоматическая смена IP системного DNS предлагается только для подтверждённого UDP-варианта; TCP, DoH и DoT требуют соответствующего транспорта в приложении или резолвере. Исходный и альтернативный варианты чередуются трижды. Каждый раунд запрашивает адрес заново. Если UDP-запрос потребовал повторения по TCP, автоматическая смена системного DNS исключается. TLS продолжает проверять исходное имя сервера; обращение к IP не отключает проверку сертификата. Изменение адреса CDN не выдаётся за доказанное вмешательство в DNS.

Различия протоколов на одном IP и порту могут проверяться повторно. Заключение сообщает о воспроизводимом рабочем варианте, а не о доказанной блокировке всего протокола.

Выводы содержат ссылки на идентификаторы измерений и следующий шаг. Недоступный ICMP, разные DNS-адреса, ошибка одной площадки или пропуск ответа маршрутизатора не превращаются в диагноз «интернет заблокирован».

## Исправления

```sh
netdiag fix --input direct.json
netdiag fix --input direct.json --apply
netdiag fix --flush-cache
netdiag fix --flush-cache --apply
netdiag fix --flush-cache --input direct.json --apply
netdiag fix --flush-cache --target example.org --apply
netdiag fix --recover /path/to/net-repair-session/state.json
```

Без `--apply` показывается инструкция. Очистка DNS-кэша с `--input` повторяет веб-проверку первой цели с ошибкой DNS до и после очистки. Если такой ошибки нет, берётся первая цель отчёта. `--target` задаёт цель явно. Автоматическое применение доступно только с интерактивным подтверждением. Реализованы очистка DNS-кэша и смена DNS одного подключения. Для смены DNS нужен свежий полный отчёт с подтверждённым решением; перед изменением выполняются новые испытания и контрольные проверки.

Показываются исходные настройки и предлагаемый DNS. После согласия запускается отдельная операция с правами администратора. Одна минимальная копия конфигурации создаётся в закрытом системном временном каталоге. Независимый процесс следит за сроком восстановления. Настройка остаётся только после успешных проверок и подтверждения в течение 30 секунд.

При неудаче выполняется откат. Если настройки изменило другое приложение или пользователь, утилита не перезаписывает их вслепую. После подтверждённого завершения временная копия удаляется. Если восстановление не подтверждено, её путь выводится для команды `fix --recover`.

Автоматическое изменение DNS поддерживается для обычных конфигураций Windows, macOS и Linux с NetworkManager. При обнаружении VPN, прокси, известных политик DNS Windows или управления Mac показывается инструкция. Не все корпоративные механизмы управления можно обнаружить. Статический IPv6 DNS Windows пока требует ручной настройки.

Изменения MTU, маршрутов, IPv6, прокси и роутера не автоматизируются. Утилита не отключает проверку сертификатов и защиту системы.

Механизм восстановления покрывает завершение или прерывание процесса при работающей ОС. Полное выключение питания и удаление временных каталогов системой не дают гарантии отката. Перед применением на важном подключении используйте ручную инструкцию и отдельно проверьте адаптер своей ОС. Автоматические изменения реальной конфигурации не входят в обычный набор тестов. На Unix отдельный тест `NETDIAG_TEST_ELEVATION=1 go test ./internal/fix -run TestElevatedSnapshotRemainsReadableByCaller` проверяет запись снимка через `sudo -n` без изменения сетевых настроек. При отсутствии беспарольного sudo этот тест пропускается; CI включает его. Атомарная замена снимка сохраняет исходного владельца и права 0600.

## Скорость без своего узла

```sh
netdiag speed --mode direct --accept-mlab-policy --max-mib 256
```

M-Lab публикует результаты вместе с внешним IP. Без согласия измерение не начинается. Условия: [политика M-Lab](https://www.measurementlab.net/privacy/) и [правила использования](https://www.measurementlab.net/aup/).

NDT7 измеряет один поток загрузки и отдачи. Загрузка считается на клиенте-получателе, отдача — по данным сервера-получателя. Если сервер не сообщил свою статистику, локальная оценка отдачи явно помечается неподтверждённой и частичной. Сохраняется доступная серверная TCP-статистика. Библиотека NDT7 не сообщает приложению причину закрытия канала результатов; этот предел отмечен в JSON. Для сопоставимых UDP-замеров буферблоата и двусторонней нагрузки нужен свой узел. Недоступность M-Lab не доказывает отсутствие интернета.

## Свой измерительный узел

Сертификат должен быть действительным для имени узла и доверенным клиентской ОС. Самоподписанный сертификат без установленного доверия клиент не принимает.

```sh
export NETDIAG_NODE_TOKEN="$(openssl rand -hex 32)"
netdiag-node --listen :8443 --udp :4444 --cert /etc/netdiag/fullchain.pem --key /etc/netdiag/privkey.pem
```

На клиенте задайте тот же токен в переменной `NETDIAG_NODE_TOKEN`, затем:

```sh
netdiag quality --mode direct --node https://node.example.org:8443 --duration 60s
netdiag speed --mode direct --node https://node.example.org:8443 --max-mib 1024
```

В PowerShell переменная задаётся через `$env:NETDIAG_NODE_TOKEN`. Для старых консолей Windows может понадобиться UTF-8.

Открываются TCP 8443, UDP 8443 для HTTP/3 и UDP 4444 для проб. Контрольные HTTPS и UDP должны доходить до одного узла с сохранением адреса клиента. Обычный HTTP reverse proxy и некоторые схемы NAT перед сервером этому не соответствуют. Доступ можно дополнительно ограничить межсетевым экраном оператора.

Узел требует токен минимум 24 байта. Сессии ограничены 600 секундами, 8 одновременными потоками и указанным сервером объёмом. Одновременно хранится не более 16 сессий. UDP-пакеты аутентифицируются, привязаны к источнику и не увеличиваются в ответе. Тестовые данные не записываются на диск.

Сессии нагрузки и UDP-контроля разделены: окончание лимита загрузки не должно выглядеть как потеря UDP. Для каждого основного этапа резервируется отдельная доля бюджета: первые одиночные потоки не расходуют данные следующих проверок. После калибровки показывается приблизительный объём для полного основного теста; при 500/500 Мбит/с это около 7 ГиБ с запасом. Повторные испытания решений используют оставшийся бюджет. При недостаточном лимите тест остаётся частичным; утилита не увеличивает лимит автоматически. Увеличивать `--max-mib` нужно и на клиенте, и на узле. Ограничения объёма относятся к обрабатываемым тестовым данным. Заголовки, служебные запросы и данные, уже находящиеся в передаче или буферах ОС, добавляют трафик; счётчик приложения не равен точному трафику интерфейса.

Контейнер собирается вне production; на рабочий сервер переносится итоговый образ:

```sh
docker build -t netdiag-node .
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges --env NETDIAG_NODE_TOKEN -p 8443:8443/tcp -p 8443:8443/udp -p 4444:4444/udp -v /etc/netdiag:/certs:ro netdiag-node --cert /certs/fullchain.pem --key /certs/privkey.pem
```

Файлы сертификата должны быть доступны UID 65532 контейнера. Docker context исключает клиент, тесты, документацию разработки, Git и файлы других ОС; в итоговом образе находятся исполняемый узел, необходимые лицензии и системная среда.

## Отчёты и приватность

По умолчанию вывод идёт в терминал, история не ведётся. `--output` создаёт JSON и не перезаписывает существующий файл. На Unix задаются права 0600; на Windows доступ зависит от ACL выбранного каталога. `--format json` пишет JSON в stdout. `--verbose` раскрывает измерения.

Отчёт содержит выбранные домены, публичные адреса целей, версии методик, измерения, испытанные варианты и заключения. Собственные цели и адрес своего узла тоже остаются в отчёте: проверьте их перед передачей. Пароль и параметры введённого URL удаляются. Токен узла, SSID, MAC, локальные адреса интерфейсов и имя пользователя не сохраняются. Недостающие RTT и джиттер в JSON представлены как `null`.

Проверки отправляют запросы выбранным сервисам и DNS-провайдерам. Это необходимо для измерения и отличается от телеметрии. Сам отчёт никуда автоматически не загружается.

Схема отчёта имеет `schema_version: 1`. Измерения имеют уникальные ID. Текстовый отчёт показывает численные результаты задержки под нагрузкой и сводку DNS, TLS, HTTP-протоколов и прочих проверок. `quality` без успешных RTT-проб возвращает ошибку измерения, а не успех. Сравнение сохраняет причины отказов, времена этапов, протоколы и статистику качества. Управляющие последовательности из импортированных отчётов очищаются перед выводом в терминал. `findings[].evidence` содержит ID исходных измерений. Смена подключения, доступной конфигурации DNS или прокси прерывает серию. Отслеживаются маршруты до шести фактических адресов HTTP/QUIC и измерительного узла. Сравниваются данные ОС для одного адреса: интерфейс и доступные сведения о следующем переходе (Windows — выбранный интерфейс). Адреса и имена физических интерфейсов используются локально для поиска шлюза под VPN и в JSON не сохраняются. При нагрузке шлюз измеряется параллельно с внешним UDP-узлом. Трассировка различает выполнение команды и фактически наблюдаемое достижение цели. Очень короткое переключение между опросами ОС может остаться незамеченным.

Коды выхода: `0` — проверка завершена без заключений уровня error; `1` — обнаружена ошибка; `2` — ошибка аргументов, доступа или сохранения; `3` — частичное измерение. Код 0 не означает доказанную исправность всех сетевых приложений.

## Сборка и разработка

Нужен Go 1.27.4 или совместимый более новый выпуск.

```sh
go test -race ./...
go vet ./...
go build -trimpath -buildvcs=false -o ../netdiag-bin/netdiag ./cmd/netdiag
go build -trimpath -buildvcs=false -o ../netdiag-bin/netdiag-node ./cmd/netdiag-node
```

При сборке Windows используйте расширение `.exe`. Для другой платформы задаются `GOOS` и `GOARCH`. Поддерживаются `amd64` и `arm64` для Windows, Linux и macOS. Кросс-компиляция не заменяет проверку работающего приложения на целевой ОС.

Движок и методики находятся в `internal/diag`, протокол узла — в `internal/node`, транзакции исправления — в `internal/fix`, интерфейс и представление отчётов — в `internal/cli`. Новое правило должно опираться на сохранённые измерения, явно задавать ограничения вывода и проходить тест с известной причиной сбоя.

Тесты используют локальные HTTP/TLS/HTTP3/DNS/UDP-стенды и адаптеры настроек в памяти. Они не требуют изменения сети компьютера и не запускают публичный тест M-Lab. Workflow CI настроен для тестов на трёх ОС и сборки обеих архитектур. Реальные проверки из российских сетей, на разных VPN и с реальным роутером остаются необходимым этапом перед стабильным выпуском.

Лицензия: Apache-2.0. Уведомления о сторонних компонентах находятся в `THIRD_PARTY_NOTICES.md`.

Адреса DNS сверяются с документацией провайдеров: [Яндекс](https://dns.yandex.ru/), [Google](https://developers.google.com/speed/public-dns/docs/using/), [Cloudflare](https://developers.cloudflare.com/1.1.1.1/ip-addresses/).
